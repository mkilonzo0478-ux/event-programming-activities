## Step 4 (Round 3): Blocked Event Loop Questions

1. **What happened to the other events while you were "stuck" on the slow handler?**
   - All subsequent events remained sitting idle in the **Event Queue** in FIFO (first-in, first-out) order. Because the single **Event Loop** thread was busy executing the 30-second handler, it could not pull or dispatch the waiting cards until that slow handler finished.

2. **What would a user see if this happened in a real application?**
   - The application's graphical user interface (GUI) would completely freeze. Button clicks, typing, scrolling, window dragging, and even window repainting (like resizing or minimizing/restoring) would appear unresponsive—often causing the operating system to dim the window and show a *"Not Responding"* message.

3. **How could this problem be fixed?**
   - Offload any long-running or blocking work (such as network requests, database queries, file I/O, or `Thread.sleep`) from the Event Loop / Event Dispatch Thread (EDT) to a **background worker thread** (for example, using `new Thread(...).start()` or `SwingWorker` in Java Swing). Once the background work completes, marshal only the lightweight UI update back onto the EDT using `SwingUtilities.invokeLater(...)`.

---

## Step 5: Written Reflection

In an event-driven application, the **event queue** acts as a thread-safe waiting line (FIFO buffer) that collects incoming events generated by event sources—such as button clicks, keystrokes, timers, and window resizes—in the exact order they arrive. The **event loop** (known as the Event Dispatch Thread, or EDT, in Java Swing) continuously monitors this queue, pulls the next event from the front, and dispatches it to its registered event handler for execution. Because a single thread typically runs the event loop and also handles painting the user interface, every handler must finish quickly and return control back to the loop. If a slow or blocking task runs directly inside the event loop, no other queued events can be processed until that task finishes. As a result, new user inputs pile up unprocessed in the queue and the screen stops redrawing, making the entire application freeze from the user's perspective. Therefore, the event loop must never be blocked; heavy computations or I/O should always be delegated to background threads so the UI stays smooth and responsive.
