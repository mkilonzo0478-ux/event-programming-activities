## Step 1: Self-Assessment Answers

### Learning Outcome 1: Define EDP Components

1. **What is an event? Give two examples.**
   - An **event** is a signal or object representing a state change or external occurrence that an application can detect and react to.
   - *Examples:* A user clicking a `JButton` (`ActionEvent`), or a timer firing after 1,000 ms.

2. **What is an event source? Give two examples.**
   - An **event source** is the component, hardware device, or software object that detects an action and generates/publishes the event object.
   - *Examples:* A Swing `JSlider` generating `ChangeEvent`s, or a physical ATM keypad generating button-press events.

3. **What is an event listener? Give two examples.**
   - An **event listener** is an object or interface registered with an event source to wait for specific events and receive notification when they occur.
   - *Examples:* Java's `ActionListener` attached to a `JButton`, or `ChangeListener` attached to a `JSlider`.

4. **What is an event handler? Give two examples.**
   - An **event handler** is the concrete method or callback logic executed when a registered listener receives an event.
   - *Examples:* The `actionPerformed(ActionEvent e)` body (or lambda `e -> { count++; ... }`) updating a counter label, or the microwave controller code that stops heating when a door-opened event arrives.

### Learning Outcome 2: Compare Paradigms

6. **How does procedural programming differ from event-driven programming?**
   - **Procedural programming** executes statements sequentially from start to finish under the program's strict control (e.g., `Scanner` prompts in `ProceduralCalculator`). **Event-driven programming** uses *inversion of control*: the program sets up components, registers listeners, and enters an event loop that reacts dynamically in whatever order the user or environment triggers events.

7. **What is the main advantage of event-driven programming for GUIs?**
   - It allows any number of on-screen controls (buttons, sliders, menus, text fields) to remain independently responsive at all times, enabling non-linear user workflows, immediate visual feedback, and easy error recovery without restarting the program.

8. **In which scenario would you choose procedural programming over event-driven?**
   - Batch scripts, command-line data-processing pipelines, one-off mathematical/ETL jobs, or deterministic startup/initialization scripts where steps follow a fixed sequence with no interactive user input.

### Learning Outcome 3: Event Loop and Queue

9. **What is the event loop? What does it do?**
   - The **event loop** is a continuous runtime loop that polls the event queue, removes the next waiting event, and dispatches it to the matching registered listener/handler, repeating until the application exits.

10. **What is the event queue? How does it work?**
    - The **event queue** is a FIFO (First-In, First-Out) buffer that holds incoming events generated by UI controls, OS inputs, and timers until the event loop is ready to process them one at a time in arrival order.

11. **Why should the event loop never be blocked?**
    - Because a single thread typically both dispatches events and repaints the GUI. Blocking it with slow work (like `Thread.sleep` or network/disk I/O) freezes the entire interface, leaves pending events stuck in the queue, and prevents screen redraws.

12. **What is the EDT in Java Swing?**
    - The **Event Dispatch Thread (EDT)** is Java Swing's dedicated single thread that runs the event loop, executes Swing event handlers, and performs all UI creation and updates. Swing components must always be created and modified on the EDT (e.g., via `SwingUtilities.invokeLater()`).

## Step 3: Week 1 One-Page Summary

### Key Definitions
- **Event:** An object or notification signaling that something happened (user click, sensor trip, timer tick).
- **Event Source:** The component/device that produces and fires the event.
- **Event Listener:** The registered observer waiting for an event from one or more sources.
- **Event Handler:** The callback logic executed in response to the event.
- **Event Queue:** FIFO waiting line holding incoming events before processing.
- **Event Loop / EDT:** Single thread continuously dequeuing events, invoking handlers, and repainting the UI.

### Core Architecture Diagram
```text
User / Hardware ---> Event Source ---> Event Queue (FIFO) ---> Event Loop (EDT) ---> Event Handler
                                           ^                                               |
                                           +---------- SwingUtilities.invokeLater() -------+
                                                  (from background worker threads)
```

### Helpful Code Patterns Learned
1. **Starting Swing safely on the EDT:**
   ```java
   SwingUtilities.invokeLater(() -> new SmartHomePrototype().setVisible(true));
   ```
2. **Attaching a concise lambda `ActionListener`:**
   ```java
   button.addActionListener(e -> countLabel.setText("Count: " + (++count)));
   ```
3. **Keeping the EDT non-blocking during slow work:**
   ```java
   new Thread(() -> {
       // slow work off EDT
       SwingUtilities.invokeLater(() -> statusLabel.setText("Done!"));
   }).start();
   ```
4. **Preventing listener/UI memory leaks:** Always remove model/list references (e.g., `createdButtons.clear()`) when removing dynamic UI components.
